## 1. 自動完了が自動取り込みより先に走り、複数端末で同期が止まる

- 重大度：高
- 分類：バグ
- 状態：完了（起動・画面復帰・10分ごとの順序を「取り込み → 自動完了」にした。`refreshThenAutoComplete()`。実機での確認はまだ）

**問題の内容と該当箇所**

起動時の処理が `app.js:3985` で `load(); autoCompleteOverdueItems();` → `app.js:3990` で `autoPullIfStale()` の順になっている。
「期限を過ぎたら自動で完了」の予定（`autoComplete`）が過ぎていると、`autoCompleteOverdueItems()`（`app.js:3740`）が先に `save()` して `db.updatedAt` を更新する。
その後の自動取り込み `autoPullWith()` は `localChanged=(localAt!==known)`（`app.js:2503`）で「この端末に未同期の変更がある」と判断し、他の端末の新しい内容を取り込まない（「自動反映していません」のトースト）。
3秒後の自動同期も、保存先の rev が進んでいるため 409 で止まる（`app.js:940` の `runAutoSync`）。
10分ごとの `setInterval`（`app.js:3989`）でも同じことが起きる。

**なぜ問題なのか**

自動完了の予定は毎週・毎日のように過ぎるので、端末を2台以上使うと「どちらの端末にも未同期の変更がある」状態が日常的に起きる。
同期が止まるたびに手動で読み込みか上書きを選ぶ必要があり、上書きを選ぶと他の端末の編集が消える（世代バックアップには残る）。

**改善案**

- 起動時と画面復帰時は、先に自動取り込み（`autoPullIfStale()` の Promise）を待ってから `autoCompleteOverdueItems()` を実行する。取り込みが失敗・不要でも、終わったら自動完了を行う
- さらに、自動完了だけの変更は「取り込みを妨げる変更」とみなさない方法も検討する。例：自動完了は保存先から取り込んだ直後に、取り込んだデータに対して改めて実行する（同じ締切は同じ結果になるので、端末間で食い違わない）

**実装担当への指示文**

## 2. 夜の再通知・週次レビューを Worker に移植する（Cron の本数上限に注意）

- 重大度：高
- 分類：使いやすさ（機能の移植）
- 状態：完了（Cron は3本にまとめた。時刻の変更と、月曜の data.json 添付を移植しないことは持ち主に確認済み。本番での実際の送信は未確認）

**問題の内容と該当箇所**

旧環境の `send_digest.sh`（雛形は `deadline-data-template/.github/scripts/send_digest.sh`）には3種類の Discord 通知がある。

- 朝（毎日 6:47）
- 夜の再通知（月〜土 20:47。`DIGEST_MODE=evening`、同ファイル 482〜530 行付近）
- 週次レビュー（日曜 21:45。`DIGEST_MODE=weekly`、`send_weekly_review`、273〜474 行付近）

Worker（`worker/src/jobs.js`・`worker/src/digest.js`）には朝の分しかない。
`docs/cloudflare-migration.md` の段階4では「Cron を有効にして旧 Actions を止める」予定だが、このままだと夜の再通知と週次レビュー（来週の見通し・1週間の達成・繰り返しの調子・負荷予報・月初めの支出まとめ）がなくなる。
月曜の朝の data.json 添付（`send_backup`）も Worker にない。

Cron Triggers は無料プランで**アカウント全体で5本まで**（[Cloudflare Workers の制限](https://developers.cloudflare.com/workers/platform/limits/)）。このWorkerだけで既に4本使っている（`wrangler.jsonc:31`）ので、2本足すと上限を超える。同じアカウントの他の Worker（例：`tournament`）が Cron を使っていれば、さらに余裕がない（要確認）。

**なぜ問題なのか**

段階4で旧 Actions を止めた日から、夜の再通知と週次レビューが届かなくなる。
Cron を単純に足すと、デプロイが失敗するか、他の Worker の Cron と取り合いになる。

**改善案**

Cron の本数を増やさず、時刻をまとめて3本に減らす（1本で複数の仕事をする）。

| Cron（UTC） | JST | する仕事 |
|---|---|---|
| `47 21 * * *` | 毎日 6:47 | 朝の締切一覧（今と同じ） |
| `23 11 * * *` | 毎日 20:23 | 翌日分のメール ＋ 月〜土は夜の再通知、日曜は週次レビュー |
| `23 20 * * *` | 毎日 5:23 | 当日分のメール ＋ 世代バックアップの間引き |

夜の再通知は 20:47 から 20:23 に、週次レビューは 21:45 から 20:23 に早まる。変更が困る場合は相談する。
1つの仕事が失敗しても、同じ Cron の他の仕事は実行し、最後にまとめて失敗として投げる（ダッシュボードの履歴に残るように）。

月曜の data.json 添付は、D1 の世代バックアップ（毎日 3:10 に間引き、30分間隔で保存）があるため、移植しない案を推す。
添付すると Discord にメモを含む全データが毎週置かれる点も、移植しない理由になる（要確認：移植しないでよいか、持ち主に確認する）。

## 3. キー違いの端末の自動通信で、同じ回線の端末ごと締め出される

- 重大度：中
- 分類：セキュリティ（使いやすさにも影響）
- 状態：完了（アプリは 401 で自動の通信を止めて一度だけ知らせる。Worker は正しいキーの成功でその IP の失敗の記録を消す。実機での確認はまだ）

**問題の内容と該当箇所**

Worker は認証の失敗を IP ごとに数え、10分に10回失敗するとその IP からの要求を 429 で止める（`worker/src/index.js:118-133`）。
アプリは、保存したアクセスキーが古い（`APP_KEY` を変えた・打ち間違えた）端末でも、10分ごとと画面復帰のたびに `/api/data` を読みに行く（`app.js:3994`・`3959` → `autoPullWith`）。
失敗は `.catch(function(){})` で黙って捨てられ、利用者には何も表示されない（`app.js:2477` 付近）。

**なぜ問題なのか**

自宅の Wi-Fi のように IP を共有していると、古いキーの端末1台が失敗を重ねるだけで、正しいキーの端末も 10 分間使えなくなる。
しかも原因が画面に出ないので、気づきにくい。

**改善案**

- アプリ：自動処理で 401 を受けたら、その起動中は自動の通信（自動取り込み・自動同期）を止め、「アクセスキーが違います。設定で入れ直してください」を1回だけ表示する。429 のときも理由を表示する
- Worker：今の仕組み（総当たりへの対策）は残す。ただし、正しいキーで認証できたときは、その IP の失敗回数を消す（`DELETE FROM limits WHERE k = ?`）。D1 への書き込みを増やさないよう、失敗の記録があるときだけ消す

**実装担当への指示文**

> 目的：アクセスキーが間違っている端末が自動通信で認証失敗を重ね、同じ IP の正しい端末まで 429 で締め出されるのを防ぐ。
> 対象ファイル：`app.js`（`cfFetchData` 2400 行付近、`autoPullWith` 2472 行付近、`runAutoSync` 940 行付近）、`worker/src/index.js`（`authorize` 118 行付近、`isLimited`・`countHit`）、テストは `test/unit/worker.test.js`・`test/unit/cf-sync.test.js`。
> やること：
> 1. `app.js`：Cloudflare の自動処理（自動取り込み・自動同期）で 401 を受けたら、モジュール内の変数で「認証失敗」を覚え、ページを開き直すか設定でキーを保存し直すまで自動の通信をしない。トーストは1回だけ「アクセスキーが違うため、自動の読み込み・同期を止めました。設定（右上の歯車）で入れ直してください」。429 なら「認証の失敗が続いたため、しばらく使えません」を1回だけ
> 2. `worker/src/index.js`：認証に成功したとき、`isLimited` で読んだ行（失敗の記録）があれば、その IP の行を消す。記録がないときは D1 に書き込まない
> 3. テスト：Worker 側で「9回失敗→正しいキーで成功→さらに9回失敗しても 429 にならない」、アプリ側で「401 を受けた後は自動取り込みが fetch しない」を確かめる
> 4. `index.html` の `app.js?v=...` と `build-stamp` を更新する
> 制約：キーやトークンをログ・画面に出さない。認証のない API を増やさない。
> 完了の条件：`npm test` と `npm run build` が成功する。コミットメッセージは `fix: 要約`。

## 10. 自動同期のたびに全データを読み直している

- 重大度：低
- 分類：性能
- 状態：完了（Cloudflare の自動同期は、全データを先に読み直さず、手元の rev を `If-Match` に付けて直接送る。衝突は Worker が 409 で断り、今までどおり止めて知らせる。Worker の `GET /api/data` は、保存してある JSON を解析し直さずに返す）

**問題の内容と該当箇所**

自動同期 `runAutoSync`（`app.js:940`）は、送る前に `fetchRemoteState` → Cloudflare では `cfFetchData`（`app.js:1007`・`2400`）で締切データ全体を GET してから PUT する。
Cloudflare の PUT は `If-Match`（rev）で衝突を検出できるので、先の GET は判定に使う rev を知るためだけになっている。
また Worker の `GET /api/data` は保存してある JSON 文字列を `JSON.parse` してから `JSON.stringify` し直して返す（`worker/src/index.js:186`）。

**なぜ問題なのか**

今のデータの大きさなら問題ない。ただし保存できる上限（約1.9MB）に近づくと、通信量が2倍になり、Worker の CPU 時間（無料プランは 10ms）を JSON の解析・再変換が圧迫する。

**改善案**

- Cloudflare の自動同期は、手元の `cf-known-rev` を `If-Match` に付けて直接 PUT し、409 のときだけ今の流れ（止めて知らせる）にする
- Worker の GET は、保存してある JSON 文字列をそのまま応答の中に埋め込む（`'{"ok":true,"rev":' + rev + ',"data":' + row.json + ...`）

**実装担当への指示文**

> 目的：Cloudflare 同期の通信量と Worker の CPU 時間を減らす。動き（衝突したら止めて知らせる）は変えない。
> 対象ファイル：`app.js`（`runAutoSync` 940 行付近の `checkedPut`）、`worker/src/index.js`（`getData` 183 行付近）、テストは `test/unit/cf-sync.test.js`・`test/unit/worker.test.js`。
> やること：
> 1. `runAutoSync` で `cfg.kind==="cf"` のときは、`fetchRemoteState` を呼ばずに `cfPut` する。`cf-known-rev` が無い端末は今までどおり送らない（自動同期の対象外）
> 2. `getData` は `JSON.parse` せず、`row.json` の文字列をそのまま組み立てた JSON 文字列の中に入れて返す（`updatedAt` は `JSON.stringify` して入れる）。ヘッダーは今の `json()` と同じにする

## 21. 端末内の古い型の締切で、自動同期が 400 で止まり、何も知らせない

- 重大度：中
- 分類：バグ
- 状態：完了（PR #93。`normalizeItemTypes` を `load()` でも使い、自動同期が 400・413・5xx で断られたら理由を1回だけトーストと設定に出す。`cf-sync.test.js` で、補正しないと Worker が 400・補正すると保存できることを確認。実際の端末に古い型の項目があったかは未確認）

**問題の内容と該当箇所**

- Worker の保存 API は、締切1件ごとの型を厳しく調べる（`worker/src/index.js` の `checkItemValues`）。対象は `rep`・`repCount`・`repDay`・`seq`・`skip`・`pick`・`done`・`allDay`・`autoComplete`・`calHide`。1件でも合わなければ、全体を 400 で断る
- アプリ側で型をそろえる `sanitizeIncomingItems`（`app.js` 191 行付近）は、取り込みの経路（読み込み・自動取り込み・世代バックアップの復元・JSON の読み込み）でしか使われない
- 起動時に端末内のデータを読む `load()`（`app.js:108`）は、「自分自身の localStorage は検証しない」というコメントのとおり、型をそろえない
- 自動同期 `runAutoSync`（`app.js:1145`）は、409（衝突）と 401・429（認証）以外の失敗の応答を、何もせず捨てる。400・413・500 では、トーストも出さず、記録も残さない

**なぜ問題なのか**

保存の検査を厳しくする前の版で書かれた、古い型の項目（例：`seq` が文字列、`skip` に日付でない値）が端末内に残っていることがある。
そうした端末では、編集のたびの自動同期が 400 で失敗し続ける。それなのに画面には何も出ない。
他の端末にも Discord の通知にも変更が届かないまま、気づくのは「最終同期が1日以上前」の警告が出たときになる。

**改善案**

- 起動時の `load()` でも、`sanitizeIncomingItems` と同じ型の補正をする。ただし、項目を隔離（一覧から外す）するのは今までどおり取り込み時だけにし、端末内のデータでは型の補正だけを行う（既存の表示を急に消さない、という今の方針を守る）
- 自動同期が 400・413・5xx で失敗したら、その理由（Worker が返す `error` の文）を1回だけトーストで出し、設定の同期の節にも「最後の自動同期は失敗しました（理由）」と出す。同じ失敗が続く間は、トーストを繰り返さない

**実装担当への指示文**

> 目的：端末内に古い型の締切が残っていても自動同期が黙って止まらないようにし、失敗したときは理由を知らせる。
> 対象ファイル：`app.js`（`load` 108 行付近、`sanitizeIncomingItems` 191 行付近、`runAutoSync` 1145 行付近、設定の同期の節 2593 行付近）、テスト `test/unit/app-logic.test.js`・`test/unit/cf-sync.test.js`。Worker（`worker/src/index.js` の `checkItemValues`）は変えない。
> やること：
> 1. `sanitizeIncomingItems` のうち「型の補正」の部分（`skip`・`repCount`・`repDay`・`seq`・`allDay`・`autoComplete`・`calHide`・`pick`・`done`・`rep`・`memo`・`cat` の補正）を、隔離をしない純粋な関数 `normalizeItemTypes(item)` に切り出す。`sanitizeIncomingItems` はそれを使う（動きは変えない）

# 第4回で追加した項目（2026-11-05）：同期の作り直し

持ち主の提案「ブラウザにデータを残さないようにし、起動時に確実に保存先から読み込む」を出発点に、円卓議論（利用者代表・懐疑派・現実派・異端者・同期の専門家の5人、3ラウンド）で比べた結果。
議論の記録は、このファイルの末尾の「第4回の円卓議論の記録」にある。

**前提として確認した事実**

- 締切データの通信（`/api/`）は、Worker が `Cache-Control: no-store` を返し、Service Worker も保存しない。古いデータが出る原因は、HTTP キャッシュではなく、「端末内（localStorage）のデータを先に表示し、裏で保存先を確認する」という作りにある
  - 起動時の確認は `refreshThenAutoComplete`（`app.js:3996`）で、最大8秒待つ
- 自動の取り込み（`autoPullWith`、`app.js:2913`）は、端末内に未同期の変更が1つでもあるとやめる
  - 判定は `db.updatedAt` と前回同期時の時刻の比較で、自動完了の保存も「変更」に数える
- 衝突はデータ全体の版（rev）で判定する。2台が別々の締切を触っただけでも 409 になる
- 409 で「上書き」を選ぶと、上書き前の内容は必ず世代バックアップに残る（Worker の `?force=1`・`?backup=1`）。ただ、何が失われるかは押す前に分からない

## 29. 自動完了を「未同期の変更」から外し、自動完了の記録の id を決まった値にする

- 重大度：中
- 分類：バグ
- 状態：完了（PR #99）

**問題の内容と該当箇所**

自動完了（`autoCompleteOverdueItems`、`app.js:3974`）は、期限を過ぎた「自動で完了」の締切を完了にして `save()` する。
`save()` は `db.updatedAt` を進めるので、自動の取り込み（`autoPullWith`、`app.js:2913`）はこれを「この端末の未同期の変更」とみなし、他の端末の更新を取り込まなくなる。
起動時は取り込みの後に自動完了を行う順序になっている（第1回の項目1）。それでも、次の場合には同じことが起きる。

- 取り込みが8秒で打ち切られたとき
- 1分ごとの確認で自動完了が走ったとき

また、完了の記録（`logCompletion`、`app.js:3444`）の id は毎回乱数で作られる。
このままでは、自動完了を「未同期の変更」から外したり、将来マージ（33）を入れたりしたとき、2台がそれぞれ自動完了した同じ締切の記録が2件になる。

**なぜ問題なのか**

自動完了は、同じデータと同じ時刻からは、どの端末でも同じ結果になる機械の処理。
これが他の端末の更新の取り込みを止めると、30（サーバー優先の起動）の「端末に未送信の変更が無ければ保存先の内容に置き換える」が、ほとんど成り立たなくなる。
円卓議論では、全員が「30 を入れるなら、これが先に必要」とした。

**改善案**

- 自動完了による保存は、「人の未送信の変更」の印を立てないようにする（保存はして、自動同期の予定にも入れる）
- 保存先の内容を取り込んだ後は、自動完了をもう一度実行し、同じ結果を作り直す
- 自動完了の記録の id を `"auto:" + 締切の id + ":" + その回の締切日時（ISO）` のように決まった値にし、記録を取り込むとき（`adoptCompletions`・`cleanCompletions`、`app.js:179`〜）に id の重複を除く
- 自動完了の EXP は 0 なので、記録が重複しても EXP は二重にならない。ただし件数の集計（週次レビューの「自動」の件数など）がずれるので、重複は除く
- 外すのは自動完了だけにする
  - 今日の一手の印とメモのチェックは人の操作で、印は朝 6:47 の Discord とメールにも使われる。これまでどおり「未送信の変更」として確実に送る

**実装担当への指示文**

> 目的：自動完了（機械の処理）が、他の端末の更新の自動取り込みを止めないようにする。あわせて、2台で自動完了しても完了の記録が重複しないようにする。
> 対象ファイル：`app.js`（`save` 140 行付近、`autoCompleteOverdueItems` 3974 行付近、`logCompletion` 3444 行付近、`cleanCompletions`・`adoptCompletions` 179〜190 行付近、`autoPullWith` 2913 行付近）、テスト `test/unit/app-logic.test.js`・`test/unit/cf-sync.test.js`。Worker は変えない。
> やること：
> 1. 「人の操作による未送信の変更があるか」を、`db.updatedAt` との比較ではなく、端末内の印（例：`store` のキー `sync-dirty`）で持つ。人の操作の `save()` で立て、送信（PUT）が成功した応答を受けてから消す。送る前や送信中には消さない
> 2. 自動完了は、データを保存して自動同期の予定に入れるが、この印は立てない（`saveAuto()` のような別の入口を作る）
> 3. `autoPullWith` の `localChanged` を、この印で判定する。印が無ければ保存先の内容に置き換え、その後に `autoCompleteOverdueItems()` をもう一度実行する（同じ結果が作り直される）
> 4. `logCompletion` で `source==="auto"` のときは、id を `"auto:"+it.id+":"+締切日時のISO` にする。手動の完了は今のまま（乱数）
> 5. `cleanCompletions` で、同じ id の記録は1件だけ残す（先に出たものを残す）
> 6. 既存の端末からの移行：印のキーがまだ無い端末では、今の判定（`db.updatedAt` と前回同期時の比較）で印の初期値を決める
> 7. テスト：
>    - 2台の端末（`cf-sync.test.js` の `world()`）で同じ自動完了の締切を開くと、片方の端末の更新が取り込まれ、409 にならず、完了の記録が1件だけになる
>    - 人がチェックや今日の一手の印を付けた後は、印が立って置き換えが起きない
>    - PUT が失敗したら印が残る
> 8. `package.json` の patch を上げる（`docs/VERSIONS.md` の決まり）
> 制約：ES5 風の書き方。ユーザーに見える文言は日本語。
> 完了の条件：`npm test` と `npm run build` が成功する。追加したテストが、修正前のコードでは失敗する。コミットメッセージは `fix: 要約`。

## 30. サーバー優先の起動（起動・画面復帰時は保存先を読み終えてから使えるようにする）

- 重大度：中
- 分類：使いやすさ
- 状態：完了（PR #101。iPhone の実機で「PC で編集 → iPhone で開く → 読み込み中の帯の後に新しい内容が出る」を確かめたら、ここに追記する）

**問題の内容と該当箇所**

起動すると、まず端末内のデータで画面を出し、裏で保存先を最大8秒確認する（`load()` の後の `refreshThenAutoComplete`、`app.js:3996`・`4249` 付近）。
その間は古い内容が見え、編集もできる。古い内容のまま編集すると、次の同期で 409（衝突）になる。
画面復帰（`visibilitychange`、`app.js:4223`）も同じ流れになっている。

持ち主の提案「起動時に確実に読み込む」は、この順序を変えることにあたる。

**なぜ問題なのか**

- 「開いたら古い」を毎日見る
- 古い画面で編集した結果の 409 で「上書き」を選ぶと、他の端末の変更が見えないまま消える。円卓議論の懐疑派は、これを今いちばん現実的な消失の筋書きとした

**改善案**

起動・画面復帰のときは、保存先を読み終えるまで「読み込み中」を出し、その間は編集させない（表示は前回の内容でよい）。

- 読めたとき：
  - 人の未送信の変更（29 の印）が無ければ、保存先の内容に置き換え、その後に自動完了を行う
  - 未送信の変更があれば、先に送る。409 なら今の確認（31 で改善）に進む
- 読めなかったとき（圏外・待ち時間の上限）：
  - 端末内のデータを「圏外のため、前回の内容（M/D HH:MM 時点）」と明示して表示する
  - 編集は今までどおりでき、送信待ちとしてためる。圏外でも完了・登録できることは持ち主の要望なので、止めない（34 は見送り）
- 待ち時間の上限は3〜5秒。それを過ぎたら待たせず、圏外の表示に切り替える
- 編集画面（登録・編集のダイアログ）を開いている間や、入力欄に文字を入れている間は、保存先の内容で置き換えない。閉じた後に置き換える
- 端末内のデータは、圏外のときの表示と送信待ちのために残す。持ち主の案の「端末に残さない」は採らない（理由は「見送った案（第4回）」）

**実装担当への指示文**

> 目的：起動・画面復帰のときに、保存先の最新の内容を読み終えてから編集できるようにし、読めないときは「前回の内容」であることを明示する。
> 前提：項目29（人の未送信の変更の印 `sync-dirty`）が終わっていること。
> 対象ファイル：`app.js`（起動処理 4249 行付近、`refreshThenAutoComplete` 3996 行付近、`visibilitychange` 4223 行付近、`autoPullWith` 2913 行付近、`openDialog` 3172 行付近、`softRender` 4232 行付近、登録ボタン・カードの操作・クイック入力）、`styles.css`、テスト `test/unit/cf-sync.test.js`。Worker は変えない。

> 1. 状態を3つ持つ：`loading`（読み込み中）・`fresh`（保存先の最新を表示中）・`offline`（読めず、前回の内容を表示中）。アクセスキーが無い端末は今までどおり（読み込みの案内カード）
> 2. 起動時と画面復帰時（前回の確認から30秒以上たっているとき）は `loading` にする。画面の上部に「読み込み中…」の細い帯を出す。登録ボタン・カードの「完了にする」「…」・クイック入力・チェック欄を押せなくする（`aria-disabled` と見た目で示す）

> 5. 登録・編集のダイアログを開いている間や、入力欄にフォーカスがある間は、置き換えを保留し、閉じた・離れた後に行う（`softRender` の考え方と同じ）

## 31. 衝突（409）の「上書き」を押す前に、失われる内容を見せる

- 重大度：中
- 分類：使いやすさ
- 状態：完了（PR #100。置き換わる／消える締切は、各締切の seq で比べる。計画の「中身が違う・完了が戻る」の細かい分類は、見せ方を簡単にするため「消える」と「置き換わる」の2つにした）

**問題の内容と該当箇所**

衝突のときの確認（`cfAskOverwrite`、`app.js:2893`）は、「OK で上書き、キャンセルで読み込み」を文で聞くだけ。
上書きすると、保存先にしか無い変更（他の端末で足した締切・完了にした締切など）が消える。それが何かは、押す前に分からない。
上書き前の内容は世代バックアップに必ず残るが、何が消えたかに気づかなければ戻せない。

**なぜ問題なのか**

30 で衝突は大きく減る見込み。それでも、圏外で編集した後などには残る。そのときに、利用者が中身を見ずに「上書き」を選ぶと、データが黙って消える。

**改善案**

確認の前に保存先の内容を読み（409 の後に `GET /api/data`）、手元の内容と締切の id ごとに比べる。
「上書きすると消える／戻るもの」を最大5件まで、タイトルで見せる。

- 保存先にだけある締切（上書きで消える）
- 両方にあるが中身が違う締切（保存先の変更が消える）
- 保存先では完了・手元では未完了の締切（完了が戻る）

確認の画面は `confirm` ではなく、アプリ内の小さな画面にする。ボタンは「読み込む（おすすめ）」と「この端末の内容で上書き」にし、既定は読み込む側にする。

**実装担当への指示文**

> 目的：衝突のときに「上書き」を選ぶ前に、上書きで失われる内容を見せ、気づかずに消すことを防ぐ。
> 対象ファイル：`app.js`（`cfAskOverwrite` 2893 行付近とその呼び出し元 `proceedSyncChecked` 3087 行付近・自動同期の 409 の扱い、`cfFetchData` 2738 行付近）、`styles.css`、テスト `test/unit/app-logic.test.js`・`test/unit/cf-sync.test.js`。

> 1. 純粋な関数 `overwriteLosses(localItems, remoteItems)` を作る。id ごとに比べ、`{onlyRemote:[…], changed:[…], doneRemote:[…]}` を返す。中身の比較は、タイトル・締切日時・完了・メモ・繰り返しなど、利用者に見える項目で行う（`seq` などの内部の値は比べない）
> 2. 409 のときは保存先を読み、`overwriteLosses` の結果をアプリ内の小さな画面（`<dialog>`）で見せる。各分類の件数と、タイトルを最大5件。どれも0件なら「上書きしても失われるものはありません」と書く
> 3. ボタンは「保存先の内容を読み込む（おすすめ）」と「この端末の内容で上書きする」。既定のフォーカスは読み込む側。上書きは今までどおり `?backup=1` 付き

## 33. 締切ごとの3方向マージ（2台で別々の締切を変えた衝突を自動で解く）

- 重大度：低
- 分類：使いやすさ
- 状態：要確認（29・30 を入れた後、32 の記録で「別々の締切だけの衝突」が月に数回以上あれば着手する。今は着手しない）

**問題の内容と該当箇所**

衝突はデータ全体の版で判定するので、2台が別々の締切を触っただけでも 409 になる。29・30 でその頻度は大きく減る見込みだが、圏外で編集した後などには残る。

**なぜ問題なのか**

まだ問題かどうか分からない（32 で測る）。
作ると、マージを誤ったときに黙ってデータが変わる。円卓議論の懐疑派・利用者代表は、409 のように目に見えないことを強く警戒した。

**改善案（着手すると決めた場合）**

前回同期した時点の内容を「基準」として端末に1つ残す。409 のとき、保存先・基準・手元の3つを締切の id ごとに比べる。

- 片方だけが変えた締切は、その変更を採用する
- 両方が同じ締切を変えたときだけ、31 の画面で人に聞く

Worker は今の If-Match／409 のまま変えない。
作る前に、次の扱いを決めてテストを書く（円卓議論の同期の専門家が挙げた、壊れやすい点）。

- 削除：片方で削除・もう片方で編集した締切は、消さずに残して知らせる
- 繰り返しの次の回：2台で別々に進めた場合の重複
- 完了の記録：id の和集合（29 で自動完了の id が決まった値になっていることが前提）
- `expCarry`：基準からの増減を足し合わせる
- テンプレート・カテゴリの並び：両方変えたら聞く
- マージ後に `sanitizeIncomingItems` を通す
- 409 が3回続いたら人に聞く

**実装担当への指示文**

> 目的：（持ち主が着手すると決めた場合のみ）2台が別々の締切を変えたときの衝突を、確認なしで自動で解く。
> 前提：項目29〜32が終わり、項目32の記録で「別々の締切だけの衝突」が月に数回以上あり、持ち主が着手すると決めていること。決めていなければ何もしない。
> 対象ファイル：`app.js`（同期の送信・409 の扱い、`syncPayload`）、テスト `test/unit/app-logic.test.js`・`test/unit/cf-sync.test.js`。Worker は変えない。
> やること：
> 1. 送信が成功したとき・保存先を取り込んだときに、その内容を「基準」として `store` のキー `sync-base` に保存する（`syncPayload()` と同じ形）
> 2. 純粋な関数 `mergeThreeWay(base, local, remote)` を作る。上の「改善案」の扱いに従い、`{merged, conflicts:[…]}` を返す
> 3. 409 のとき、保存先を読んで `mergeThreeWay` をかける。`conflicts` が空なら、`merged` を保存先の rev を If-Match に付けて送る（409 が続けば最大3回までやり直し）。空でなければ 31 の画面で人に聞く
> 4. 「改善案」に挙げた場面それぞれの表形式のテストを書く。マージ後のデータが Worker の保存の検査を通ることも確かめる
> 5. 自動で合わせたときは「他の端末の変更と合わせて保存しました（N件）」とトーストで知らせる（黙って変えない）
> 完了の条件：`npm test` と `npm run build` が成功する。コミットメッセージは `feat: 要約`。

## 35. Scriptable のウィジェット（購読済みのカレンダーを端末内で読んで表示する）

- 重大度：低
- 分類：使いやすさ
- 状態：実装済み（実機の確認待ち。分類 `CATEGORIES` が読めるかは未確認のため、分類は使わずに作った。ホーム画面の表示と、完了後に消えることは持ち主が実機で確かめる）

**問題の内容と該当箇所**

- 締切をホーム画面で見る手段は、iOS 標準のカレンダーウィジェットだけ。購読カレンダー（`/ics/<FEED_TOKEN>.ics`、`worker/src/index.js` の `serveIcs`）の予定が、ほかの予定と混ざって並ぶ。残り日数や締切だけの並びなど、締切アプリらしい見せ方ができない
- 持ち主は、カレンダーの購読はそのまま残したい

**なぜ問題なのか**

締切は「あと何日か」が大事だが、標準のウィジェットは予定の開始時刻で並べるだけ。アプリを開かないと、急ぐ締切が分からない。

**改善案**

Scriptable（iOS の無料アプリ）のスクリプトで、iPhone がすでに購読しているカレンダー「締切トラッカー」の予定を、`CalendarEvent` で端末内から読んでウィジェットに描く。

- 通信も鍵も使わない。Worker・アプリ・購読の .ics は変えない。購読はそのまま残る
- 端末に新しい秘密を置かない（`APP_KEY` も購読 URL もスクリプトに入れない）
- 繰り返しの締切は、iOS が展開済みの予定として読める（.ics の RRULE・EXDATE を自分で解かなくてよい）
- .ics は未完了の締切だけを出すので、完了した締切は購読の次の更新で消える

議論で挙がった限界（承知の上で採用する）：

| 限界 | 中身 | 対処 |
|---|---|---|
| 更新の遅れ | 完了・登録の反映は、iOS が購読を取り直すまで待つ。.ics は更新の目安を1時間と伝えているが、実際の間隔は iOS が決める | 「最終更新」の時刻は出さない（iOS の取り直しの時刻はスクリプトから分からない）。急ぐときはアプリを開く、と割り切る |
| 分類が読めない見込み | .ics の `CATEGORIES`（分類）は、Scriptable の `CalendarEvent` からは読めない見込み（要確認） | 最初に実機で確かめる。読めなければ分類なしで作る。分類がどうしても要るときは、別の取り方を改めて検討する（決勝で2位以下だった案。ここには記載しない） |
| 締切の時刻の読み方 | .ics の予定は「締切の30分前〜締切」（期間つきは「開始〜締切」）で、締切は予定の終了時刻にある。終日の締切は、終了が翌日 0:00 になる（`worker/src/ics.js` の `vevent`） | 締切＝`endDate`。終日（`isAllDay`）なら `endDate` の前日を締切日とする |

**実装担当への指示文**

> 目的：iPhone のホーム画面に、締切を残り日数つきで並べる Scriptable のウィジェットを作る。データは、iPhone が購読しているカレンダー「締切トラッカー」から端末内で読む。
> 前提：iPhone で `/ics/<FEED_TOKEN>.ics` を購読済みで、カレンダー名が「締切トラッカー」（.ics の `X-WR-CALNAME`）になっていること。Scriptable が入っていること。
> 対象ファイル：新規 `widgets/scriptable/deadlines.js`（Scriptable 用のスクリプト。`scripts/build.mjs` の配信対象には入れない）、`README.md`（使い方の節）。Worker・`app.js`・`index.html` は変えない。
> やること：
> 1. 最初に、実機の Scriptable で `CalendarEvent` の予定から分類（`CATEGORIES`）が読めるかを確かめ、結果をこの項目の「状態」に書く。読めなければ、分類は使わない
> 2. `Calendar.forEventsByTitle('締切トラッカー')` でカレンダーを取り、`CalendarEvent.between(30日前, 14日後, [cal])` で予定を読む。30日前からにするのは、締切を過ぎた未完了の締切も .ics に残っているため
> 3. 締切は `endDate`。`isAllDay` のときは `endDate` の前日を締切日とする。締切の早い順に並べ、残り日数を「超過」「今日」「明日」「あと N 日」で出す
> 4. ウィジェットの大きさ（`config.widgetFamily`）で件数を変える（小 3件・中 4件・大 10件程度）。超過と今日は目立つ色にする（アプリの状態色の考え方に合わせ、色だけでなく文字でも分かるようにする）
> 5. タップでアプリを開く。アプリの URL はスクリプトに書かず、ウィジェットの「Parameter」（`args.widgetParameter`）で渡す。空なら何も開かない
> 6. `widget.refreshAfterDate` を、次の締切の時刻か 30 分後の早いほうにする（「今日」「超過」の切り替わりを早く反映するため。実際の更新は iOS が決める）

> 8. `README.md` に「iPhone のウィジェット（Scriptable）」の節を足す：スクリプトの入れ方、カレンダーへのアクセスの許可、Parameter にアプリの URL を入れること、更新は購読の取り直し待ちであること

## 36. 世代バックアップから実際に戻す手順を書き、一度戻して確かめる

- 重大度：高
- 分類：運用
- 状態：未着手（実地の確認は持ち主の作業）

**問題の内容と該当箇所**

- 世代バックアップ（D1 の `snapshots`）と、戻す画面（`app.js:2243` の `snapshotSection`、`app.js:2890` の `cfRestoreSnapshot`）、手順（`README.md` の「世代バックアップから戻す」）はそろっている
- しかし、本番のデータで実際に戻して、件数・繰り返し・完了の記録が元どおりになるかを確かめた記録がない
- 世代バックアップは締切データと同じ D1 にある。D1 そのものが失われると、両方を失う。D1 の外の写しは、手動の「JSONで書き出す」（`app.js:2603`）だけ

**なぜ問題なのか**

バックアップがあることと、戻せることは別。締切データが消えたときに初めて手順を試すと、手順の誤りや、戻したあとの同期の食い違いにその場で気づくことになる。

**改善案**

1. 一度、本番で戻す練習をする。戻す前の内容は自動で世代バックアップに残る（`?backup=1`）ので、練習のあとに元へ戻せる
